# Availability, restrictions, and reported failures

Reviewed on 2026-09-16. Assess a feature against the SDK, deployment target,
runtime, store implementation, and CloudKit setting. A public symbol, accepted
macro, successful local fetch, and working system integration are different
levels of evidence.

## Identify the applicable storage contract

Apple explicitly documents that [DefaultStore](https://developer.apple.com/documentation/swiftdata/defaultstore)
uses Core Data underneath. Core Data diagnostics and its CloudKit model rules
can therefore explain behavior of SwiftData's default store. This is a
documented implementation boundary, not a reason to assume that every Core Data
API or feature is exposed through SwiftData. Check custom data stores separately;
do not use private backing-object access or direct SQLite edits as a workaround.

| Reported limitation | Evidence-based interpretation | Guidance |
| --- | --- | --- |
| A feature works locally but fails with CloudKit | Documented additional model constraints | Check defaults, optional relationships, inverses, uniqueness, and delete rules in [CloudKit guidance](cloudkit-and-surfaces.md) |
| Sectioned fetching is unavailable | Availability changed: sectioned query support arrives with iOS 27 / macOS 27 | Gate the actual API and key-path type; see [queries](queries-and-history.md) |
| Models cannot use inheritance | Persistent inheritance is supported from iOS 26 / macOS 26 | Distinguish inheritance from protocol-based query failures; see [modeling](modeling.md) |
| An unversioned first release cannot migrate | Apple DTS explicitly describes a supported path | Reconstruct the original complete schema and test an actual unversioned store; see [migrations](migrations.md#starting-from-an-unversioned-store) |
| Migration failures must be application mistakes, or must be framework bugs | Both implementation/environment problems and Apple-confirmed historical bugs exist | Diagnose the underlying failure and version; do not infer the cause from an opaque top-level error |
| A property cannot be renamed | API aliases, local attribute migration, and CloudKit field identity differ | `originalName` does not promise the old cloud key; check [rename guidance](cloudkit-and-surfaces.md#renaming-a-synced-property) |
| A predicate compiles, so it must be usable in a fetch | Macro acceptance does not prove store translation or correct results | Execute the actual descriptor and affected optimization/runtime path |
| An exposed option must work end to end | Documentation describes intent; runtime behavior still needs evidence | For Spotlight, see the dated report below |

## Reciprocal inverse annotations

A [June 2023 first-person account](https://www.swiftyplace.com/blog/how-to-convert-a-coredata-project-to-swiftdata)
reports circular-reference errors in relationship code generated by Xcode's
Core Data conversion assistant, resolved by removing one side's annotation.
This establishes an early report of the symptom, not a confirmed root cause
for every similar application failure.

The following synthetic shape produces a macro circular-reference diagnostic
with Xcode 27.0 build `27A266a`. Removing the second `inverse:` annotation passes
type checking while retaining both relationship properties:

```swift
import SwiftData

@Model final class Parent {
    @Relationship(inverse: \Child.parent) var children: [Child]? = []
    init() {}
}

@Model final class Child {
    @Relationship(inverse: \Parent.children) var parent: Parent?
    init() {}
}
```

This verifies a compiler failure for reciprocal explicit inverse declarations;
it does not show that bidirectional relationships are unsupported. Apple's
[model relationship example](https://developer.apple.com/documentation/swiftdata/defining-data-relationships-with-enumerations-and-model-classes)
specifies the inverse on one side. Runtime inverse maintenance, delete rules,
and CloudKit behavior require their own checks.

## Spotlight: historical staff-confirmed symptom, current outcome unknown

The [`.spotlight` option](https://developer.apple.com/documentation/swiftdata/schema/attribute/option/spotlight)
documents Spotlight indexing intent. In an [Apple Developer Forums thread](https://developer.apple.com/forums/thread/740646),
developers reported no visible effect in October 2023 and August 2024. In April
2025 an Apple DTS engineer also reported being unable to make it work and
requested Feedback; a participant supplied `FB17371480`. The thread does not
identify a precise affected OS range or a public resolution.

Do not describe the option as universally functional merely because it exists,
or universally inert based on that history. No current end-to-end Spotlight
verification was performed for this skill. If search integration is required,
test indexing, updates, deletion, and opening results on the target OS. When
that path fails, consider supported explicit indexing via
[Core Spotlight](https://developer.apple.com/documentation/corespotlight/cssearchableindex)
after checking the app's requirement; it is a candidate alternative, not a
demonstrated repair of `.spotlight`.

## Designing synthetic checks

Use disposable disk stores, synthetic records, and `cloudKitDatabase: .none`
unless cloud behavior is the question. Useful comparisons include:

- Seed an unversioned store with one executable, then migrate the unchanged
  model as V1 to a V2 with an optional field; reopen in a separate process.
- Compile reciprocal inverse declarations and the single-inverse alternative.
- Execute equivalent generic and concrete predicate descriptors under the
  affected optimization modes, preserving the failing query shape.

These are proposed experiments, not asserted outcomes. Record the SDK, runtime,
configuration, actual results, and gaps. A passing small fixture cannot establish
that every related configuration works or that an earlier failure was user error.
